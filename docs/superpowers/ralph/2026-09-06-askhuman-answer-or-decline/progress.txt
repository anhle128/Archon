## Codebase Patterns

### Claude Ask resume uses a provider-owned prompt and never forks
- **Where**: `packages/providers/src/claude/provider.ts`
- **Pattern**: `buildClaudeAskResumePrompt` formats answer/decline blocks and a continuation instruction. Non-empty `resumeInteractions` requires `resumeSessionId`, forces `forkSession: false`, skips subprocess retries, logs only `{ errorClass }` on `claude.ask_resume_failed`, and replaces isError `errors` with `Could not resume the AskHuman session`.
- **Example**: `const queryPrompt = hasAskResume && resumeInteractions ? buildClaudeAskResumePrompt(resumeInteractions) : prompt;`

### Ask re-entry maps rows in runLayers; first stream pass only
- **Where**: `packages/workflows/src/dag-executor.ts`
- **Pattern**: `executeDagWorkflow` loads `listPendingInteractions` once, rejects any `pending` row, and fails on answered Ask `node_id`s missing from static DAG step names (`<loopGroupId>.<bodyNodeId>` included). `mapAnsweredAskResume` sorts by `created_at` then `id`, parses `askAnswerBodySchema`, maps decline to `{ payload: 'declined', declined: true }`, and requires one shared non-empty `provider_session_id`. Command/prompt/loop get `resumeInteractions` only on the first stream pass of the first resumed iteration, with `forkSession: false` and zero engine retries. Resume failures log `workflow.ask_resume_failed` with ids only and write `Could not resume the AskHuman session`.
- **Example**: `const askResume = mapAnsweredAskResume(ctx.answeredAskRows, stepNamePrefix + node.id);`

### Ask hydrate skips a second resume CAS
- **Where**: `packages/workflows/src/executor.ts`
- **Pattern**: `inspectResumableRun` lists pending interactions after the DAG snapshot. Pending Ask rows throw `Answer or decline the Ask before resuming run <id>` and never claim. Answered Ask rows (`kind === 'ask' && status === 'answered'`) make a first-node run resumable via internal `hasAnsweredAsk`. `hydrateResumableRun` returns the candidate as `preCreatedRun` without `resumeWorkflowRun` only when `status === 'running' && hasAnsweredAsk`; failed/paused/cancelled still CAS.
- **Example**: `const alreadyRunningFromAsk = candidate.status === 'running' && inspected.hasAnsweredAsk;`

### Ask answer route keeps real operations; auto-resume is ask-answer
- **Where**: `packages/server/src/routes/api.ts`, `packages/server/src/routes/api.workflow-runs.test.ts`
- **Pattern**: Import and decorate `askAnswerBodySchema.openapi('AskAnswerBody')`. Register POST `/api/workflows/runs/{runId}/ask/{requestId}/answer` via `registerOpenApiRoute`. Keep real `answerAskHuman`; mock `resolvePendingInteraction` plus typed pending errors on `@archon/core/db/workflow-pending-interactions`, and map `X-Archon-User` through `@archon/core/db/users`. `tryAutoResumeAfterGate(run, 'ask-answer', actorUserId)` only after `resumed === true`. Intermediate answers and non-web parents return 200 without dispatch.
- **Example**: `await tryAutoResumeAfterGate(result.run, 'ask-answer', requester?.userId)`

### Operations own post-commit Ask signals; resume never calls resumeWorkflowRun
- **Where**: `packages/core/src/operations/workflow-operations.ts`
- **Pattern**: `answerAskHuman` authorizes the starter (`actorUserId` required, must equal non-null `run.user_id`, no admin override), calls `resolvePendingInteraction` once, then logs `workflow.ask_resolved` and emits identifier-only `interaction_resolved` only after that promise resolves. Return the pre-resolution run. `resumeWorkflow` lists pending rows, rejects any `pending` status, and accepts `running` only when at least one Ask row is `answered`. Do not call `resumeWorkflowRun` from either operation. Mock `../db/workflow-pending-interactions` and `@archon/workflows/event-emitter` before importing operations tests.
- **Example**: `getLog().info({ workflowRunId, nodeId, toolUseId, declined, resumed }, 'workflow.ask_resolved')`

### Live interaction_resolved is identifier-only; persisted mapper branches on purged
- **Where**: `packages/workflows/src/event-emitter.ts`, `packages/server/src/adapters/web/workflow-bridge.ts`, `packages/adapters/src/chat/slack/workflow-bridge.ts`
- **Pattern**: Live `InteractionResolvedEvent` is `{ type, runId, nodeId, resumed }` only. The web live mapper emits `workflow_status` with `status: event.resumed ? 'running' : 'paused'`. The persisted mapper checks `data.purged` first (`terminal_status === 'failed'` → failed, else cancelled), then `data.resumed` (true → running, missing/unknown → paused). Add the type to `DASHBOARD_SOURCE_EVENT_TYPES`. Slack handles the case with `break` and sends no message. Never copy toolUseId/envelope/answer/questions/options/approval onto SSE.
- **Example**: `status: event.resumed ? 'running' : 'paused'`

### Resolve is on the pending store port; purge is not
- **Where**: `packages/workflows/src/store.ts`, `packages/core/src/workflows/store-adapter.ts`
- **Pattern**: Add only `resolvePendingInteraction(input: ResolvePendingInteractionInput): Promise<ResolvePendingInteractionResult>` to `IWorkflowPendingInteractionStore`. Adapter delegates to the core DB helper. Do not add purge to the port. Each test file owns its own typed stub; do not introduce a cross-suite mock factory.
- **Example**: `resolvePendingInteraction: input => workflowPendingInteractionDb.resolvePendingInteraction(input)`

### Terminal purge is query-scoped; workflows.ts calls in
- **Where**: `packages/core/src/db/workflow-pending-interactions.ts`, `packages/core/src/db/workflows.ts`
- **Pattern**: `purgePendingInteractionsInTransaction` takes the caller's `query` and must not open a nested transaction. It selects pending rows in store order (`created_at ASC, id ASC`), CAS-updates only `pending` → `purged` with `resolved_at`, leaves `answer`/`resolved_by` null, and writes one id-only `interaction_resolved` event. `workflows.ts` may import this helper; the reverse import is a cycle. Call purge only after a winning status CAS. `failOrphanedRuns` locks running ids first, updates that set, then purges each selected id.
- **Example**: `await purgePendingInteractionsInTransaction(query, id, 'cancelled')`

### Query-scoped resume is shared, callers own the transaction
- **Where**: `packages/core/src/db/workflow-resume-transition.ts`
- **Pattern**: `resumeWorkflowRunInTransaction` takes an already-open `query`. `'standard'` keeps failed/paused/cancelled/stale-running; `'paused-ask'` matches only `status = 'paused'`. `workflow-pending-interactions.ts` must not import `workflows.ts` (cycle). Public `resumeWorkflowRun` still owns CAS-miss probe and final select.
- **Example**: `resumeWorkflowRunInTransaction(query, id, dialect, 'paused-ask')`

### Canonical AskHuman contracts live in the engine schema module
- **Where**: `packages/workflows/src/schemas/pending-interaction.ts`
- **Pattern**: Import `z` from `@hono/zod-openapi` and derive types with `z.infer`. Answer/resolve objects use `.strict()`. `askHumanQuestionSchema` is exported without `.strict()` so AskHuman's accepted question shape stays unchanged. `@archon/providers/types` may add `ResumeInteraction` but must not import `@archon/workflows`.
- **Example**: `askAnswerBodySchema` is a two-arm union of `{ answers: [...] }` (min 1) and `{ decline: true }`; mixed bodies fail because both arms are strict.

### Providers contract types stay SDK-free
- **Where**: `packages/providers/src/types.ts` (`SendQueryOptions`)
- **Pattern**: Add provider-neutral resume fields on `SendQueryOptions`; do not thread answers through node prompts.
- **Example**: `resumeInteractions?: readonly ResumeInteraction[]`
